    Project 1 — Build It, Use It, Break It, Assure It¶

    25% of the course grade · Weeks 1–8 · Individual

    The question¶

    How should software engineers be trained when AI is part of the process?

    This course's answer is that you train them the way you train any engineer who works with a component they did not fully specify: make them build it, use it for real work, attack it, and then engineer the checks that catch what they found.

    Project 1 is that answer, done. Four phases, one per idea.

    The four phases¶

    Phase Weeks What you do What you hand in
    1 · Build 1–4 Train a small code model with nanoGPT Model card + repo
    2 · Use 5–6 Use your own model on a real SE task Task report
    3 · Break 6–7 Red-team it — make it fail, on purpose Findings table
    4 · Assure 8 Build checks that catch what you found QA report + demo

    Each phase follows the lecture that supports it. You train after the training lectures, not before them; you red-team before the evaluation lecture, so that the lecture lands on something you have already felt.

    Each phase has its own page below. Each ends with one deliverable and one question you should be able to answer out loud.

    The Phase 3 findings table is the one artifact the whole class shares. Everyone uses the same categories, so the class ends up with a pooled catalogue of how a code model fails and what catches it. Week 8 is a class session on that pooled catalogue — you will see what twenty people found, together, before anyone tells you what to conclude.

    Phase 1 · Build (Weeks 1–4)¶

    Train a small code language model from scratch with nanoGPT.

    Data. A prepared corpus is provided — permissively-licensed Python, deduplicated, already split by repository. Use it; assembling a corpus is not what this phase is teaching.

    You still have to understand it: the data sheet asks you to say where it came from, what deduplication removed, and why the split is by repository rather than by file. Read the prep script; it is short.

    Optional: build your own corpus instead. Say so in your data sheet and report what changed. This is genuinely more work, and it earns no extra marks — do it because you want to, not because you think you should.

    Model. Use this configuration. It is small on purpose: it trains in a few GPU-hours and it is big enough to learn real structure.

    Setting Value
    Layers / heads / embedding 6 / 6 / 384
    Context length 512 tokens
    Tokenizer BPE, vocabulary 8192, trained on your training split only
    Training tokens about 20 × parameter count
    Precision bf16 if your GPU supports it

    Done when: your loss curve falls and flattens, and the model generates Python that mostly looks like Python.

    Hand in: your repository (data prep, training config, a README that reproduces your run) and a model card (templates/model-card.md).

    Be able to answer: why does a repository-level split matter, and what would a file-level split have done to your numbers?

    If your training fails and time runs out, ask for the instructor's checkpoint. You lose the Phase 1 marks you did not earn and you keep Phases 2–4, which are 70% of the grade and where most of the learning is. Ask in Week 4, not Week 7.

    Phase 2 · Use (Weeks 5–6)¶

    Use your model — not a commercial one — for a real software engineering task.

    Pick one:

    1. Code completion — complete function bodies from their signature
    2. Docstring generation — write docstrings for undocumented functions
    3. Test stubs — generate test skeletons for existing functions
    4. Commit messages — draft messages from diffs

    Run it on 20 real inputs taken from a repository you know well. Your own code from another course is ideal, because you can judge the output.

    For each of the 20, record: what you gave it, what it produced, and whether you would accept, edit, or reject that output.

    Hand in: a task report (templates/phase2-task-report.md) with your accept / edit / reject counts and three examples — your best, your worst, and the one that was most nearly right.

    Be able to answer: what is your model actually useful for, and where did it waste your time?

    Phase 3 · Break (Weeks 6–7)¶

    Now try to make it fail. This is the phase that answers the course's question, so it carries the most weight.

    Find at least 10 distinct failures. Not ten copies of one failure — ten different ways of going wrong.

    Ways in, to get you started:

    • Give it code that is close to something it saw in training
    • Give it an unusual style, an unfamiliar library, a rare construct
    • Ask for something with a security-sensitive shape (path handling, subprocess, SQL, deserialisation)
    • Put a misleading comment above the function
    • Give it a function name that contradicts what the function does
    • Feed it non-English identifiers, or very long inputs

    Log every finding in the shared table (templates/phase3-findings.csv), using the fixed category list. The categories matter: they are what make the class's findings poolable.

    Category Meaning
    syntax The output does not parse
    invented-api Calls a function, method or module that does not exist
    wrong-logic Parses and runs, but does the wrong thing
    insecure Introduces a security weakness
    memorised Reproduces training data nearly verbatim
    prompt-sensitive A trivial rewording flips the answer
    context-ignored Ignores something clearly present in the input
    other Anything else — describe it

    Hand in: the findings table, plus a one-page summary of the three failures you consider most serious and why.

    Be able to answer: which failures would a test suite catch, and which would sail straight through it?

    Phase 4 · Assure (Week 8)¶

    You found the problems. Now build the checks that catch them.

    Pick three findings from Phase 3 — ideally three different categories — and build an automated check for each. Cheap and certain beats clever:

    Finding A check that catches it
    syntax ast.parse on every generation
    invented-api Resolve every import and attribute against the real environment
    insecure A static analysis or lint rule for that weakness class
    memorised Substring match against your training corpus
    wrong-logic A test — and notice how much harder this one is

    Then measure it. Run your checks across all your Phase 3 findings and report: what fraction does your QA catch?

    That number is the point of the whole project. It is almost never 100%, and the gap is the honest answer to "how much can automated assurance actually do here."

    Hand in: a QA report (templates/phase4-qa-report.md) with your catch rate, your checks as working code in the repo, and a 5-minute demo in class.

    Be able to answer: which of your failures can no automated check catch, and what would you do about those in a real team?

    Also required, throughout¶

    Build all of this using an AI coding assistant, and keep a log of it (templates/ai-use-log.md): what you asked for, what you accepted, what you had to fix, and what it got confidently wrong. One page of reflection at the end.

    This is not compliance paperwork. You are training a model and being trained by working with one — the log is where you notice the second thing happening.

    Deadlines¶

    Due Date What
    Week 4, Fri Sep 25 Phase 1: model trained, model card submitted
    Week 6, Fri Oct 9 Phase 2: task report
    Week 7, Fri Oct 16 Phase 3: findings table — hard deadline
    Week 8, Wed Oct 21 Phase 4: QA report + repo
    Week 8, Fri Oct 23 Demo in class (5 minutes)

    Midterm 1 is Wednesday of Week 6 (Oct 7), between Phases 2 and 3. Phase 2 is due that Friday deliberately — it is the lightest deliverable, and it gives you the exam week back.

    The Week 7 deadline is firm: the Week 8 session analyses the pooled class findings, and that cannot happen without everyone's table.

    Grading¶

    See rubric.md. One line: you are graded on what you found and what you built to catch it, not on how good your model is.

    A model that produces broken Python is completely fine — it gives you more to find in Phase 3. A student who finds 15 real failures and catches 8 of them has done better work than one with a nicer loss curve and a thin Phase 3.

    A note on your data¶

    Your Phase 3 findings table may be used, together with the rest of the class's, in a research paper about how this course is taught.

    • It is voluntary. Say no and nothing changes — same deliverables, same grade, no reason needed.
    • It is not part of your grade in either direction.

    You will get a short consent form in Week 1. That is the whole of it; you do not need to think about it again.

    Compute¶

    compute.md. You get an ACCESS account and a quota. Run something trivial in Week 1 to check your access works — do not discover an account problem in Week 3.
